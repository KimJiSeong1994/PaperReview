# 블로그 콘텐츠 가이드 (SEO·GEO)

검색엔진과 생성형 엔진(ChatGPT/Perplexity/Claude/AI Overviews)에서 집현전 블로그가 발견·인용되도록 돕는 작성 컨벤션.

## ⚠️ 전제 — 온페이지보다 "권위·배포"가 먼저
신규 사이트(도메인 권위·백링크 ≈ 0)에서는 **아래 온페이지 작성 기법만으로는 검색 트래픽이 거의 늘지 않습니다.** 먼저 해결할 것:
1. **배포 채널** — 제품이 개발자/연구자 도구이므로 **MCP 생태계 등록**(→ `docs/mcp-distribution.md`)이 최고 레버리지. 그다음 커뮤니티(GeekNews·HN·Reddit), **Naver 블로그 크로스포스트**(canonical).
2. **검색 수요 있는 글** — "우리가 기능 X를 만들었다"식 제품 일기는 검색 수요가 거의 없음. 사람들이 실제로 검색하는 질문(비교·하우투·튜토리얼)을 다루는 글을 추가.
3. **백링크·색인** — 한국 AI/ML 커뮤니티·강의 자료에서 링크 확보.

아래 작성 기법은 **위가 갖춰진 뒤(또는 신규 글 작성 시) 적용**하는 품질 레이어다.

## 시스템이 자동 처리 (작성자 불필요)
- SSR: 발행 글은 JS 없이 본문·메타·JSON-LD 노출 · `BlogPosting` JSON-LD/OG/Twitter 메타는 제목·excerpt로 자동 생성 · `sitemap.xml`·`feed.xml`·`llms.txt` 자동 포함 · 한글 여부로 `inLanguage`·`og:locale` 자동 판별.

## 작성 체크리스트 (근거 강한 순)
1. **주요 주장을 이름 있는 출처와 링크로 연결** — 논문명·저자와 실제 원문(arXiv/DOI/공식 PDF)을 함께 제시해 독자가 근거를 확인할 수 있게 한다. 출처 표시는 검증 경로이며 노출·인용 상승을 보장하지 않는다.
2. **필요하고 검증된 통계·수치·결과** — 원문이 보고한 숫자는 데이터셋·지표·비교 조건과 함께 쓴다. 글마다 수치를 의무로 넣거나 원문에 없는 효과 크기를 만들지 않는다.
3. **첫머리 2~4문장 요약** — 핵심 질문에 곧장 답하면 사람·엔진 모두 추출이 쉽다. excerpt에도 재사용. (만능은 아님 — "최대 GEO 요인"은 과장이라 검증으로 정정.)
4. **엔티티 명시** — 집현전/Jiphyeonjeon, 다루는 논문·저자를 이름으로 분명히.
5. **추출 가능한 구조** — 명확한 H2/H3, 리스트/표. 길고 자연스러운 곳엔 Q&A도 좋다.
6. **키워드 스터핑 금지** — 측정상 역효과(Helpful Content). 연구자 독자 기준으로 자연스럽게.
7. **비교의 역할과 조건 구분** — 예측 모델·표현 학습·사후 설명·기준선 개선을 대체 가능한 방법처럼 나열하지 않는다. 예측 단위, 일반화 설정, 학습 목적을 구분하고 보고된 실험 조건을 아키텍처의 불가능 조건으로 일반화하지 않는다.
8. **모델·비용 단계 구분** — 검색·통합·최종 생성 모델과 색인·학습·질의 비용을 분리한다. 핵심 비교 앞에는 순위가 아니라는 짧은 안내를 두고, 상세 근거에는 해석 한계·알려진 사실·미보고·해당 없음 상태와 모든 출처를 보존한다.
9. **시작과 비교를 먼저 보여주기** — 시리즈 소개 뒤 실제 공개된 첫 논문을 제시한다. canonical `reading_guide[].slugs`는 전체 시리즈 순서를 중복·누락 없이 나누며, 짧은 단계 이동과 상세 읽기 목록이 같은 그룹을 사용한다. 비교 항목의 `summary.role`, `summary.fit`, `summary.caution`은 각각 100자 이하로 역할·적합한 상황·주의점을 설명한다. 요약은 원문에 근거한 편집이며 성능 순위나 상세 근거의 대체물이 아니다.

## 주의 (비판 검토 반영)
- **FAQ는 "리치 결과 SEO 수단"이 아니다** — Google은 2023년 FAQ 리치 결과의 정기 노출을 잘 알려진 권위 있는 정부·보건 사이트 중심으로 제한했다([공식 안내](https://developers.google.com/search/blog/2023/08/howto-faq-changes)). 일반 논문 리뷰에서는 실제 독자 질문을 설명할 때만 선택한다.
- **모든 글에 동일 템플릿(요약+FAQ+질문형 헤딩+날짜)을 기계적으로 붙이지 말 것** — 이 블로그의 강점인 "솔직하고 깊은 기술 톤"을 해칠 수 있다. 글 성격에 맞게 **선택 적용**.
- **신선도(날짜) 표기는 실제 갱신이 있을 때만** — 내용 변화 없는 날짜 갱신("가짜 신선도")은 패널티 위험.
- **Naver(국내 검색 ~60%대)는 신호가 다르다** — C-Rank(작성자 권위)·DIA(품질/의도)·참여도 중심. 위 Google식 온페이지 기법 효과가 제한적. 한국어 노출은 **Naver 블로그 크로스포스트 + 참여**가 더 효과적.

## 측정
- 발행 뒤 같은 질문을 여러 서비스에 직접 묻는 점검은 화면 동작을 보는 탐색적 확인으로만 기록한다. 재현 가능한 인용률 측정이나 인과 효과로 해석하지 않는다.
- 서버 로그(`middleware.py`)의 AI crawler fetch 추정치와 실제 AI referrer 유입을 분리한다. 둘을 인용·클릭과 합치지 않는다.
- Google Search Console / Naver Search Advisor의 실제 유입 쿼리로 "무엇으로 노출되는지" 확인한다. 계정 접근 불가와 데이터 부족은 관측 0이 아니다.
- 작은 파일럿의 방향성 변화로 인용 증가율이나 검색 성장을 약속하지 않는다.
